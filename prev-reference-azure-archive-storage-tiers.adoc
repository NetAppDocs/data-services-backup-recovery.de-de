= Unterstützte Azure-Archivzugriffsebenen mit NetApp Backup and Recovery
:hardbreaks:
:allow-uri-read: 
:nofooter: 
:icons: font
:linkattrs: 
:imagesdir: ./media/


[role="lead"]
NetApp Backup and Recovery unterstützt die Azure Archive-Zugriffsebene, um ältere Sicherungen zur Senkung der Storage-Kosten in diese Ebene zu verschieben. Archivierte Sicherungen verursachen höhere Kosten und ihre Wiederherstellung dauert länger, daher sollten die Wiederherstellungskosten und Abrufzeiten vor dem Tiering von Sicherungen geprüft werden.



[[supported-azure-blob-access-tiers-for-netapp-backup-and-recovery]]
== Unterstützte Azure Blob-Zugriffsebenen für NetApp Backup and Recovery

Beim Erstellen von Sicherungsdateien werden diese zunächst in der Zugriffsebene „Cool“ gespeichert. Diese Ebene ist für die Speicherung von Daten optimiert, auf die selten zugegriffen wird, die aber bei Bedarf sofort verfügbar sind.

Wenn auf Ihren Quellclustern ONTAP 9.10.1 oder höher ausgeführt wird, können Backups nach einer bestimmten Anzahl von Tagen (in der Regel mehr als 30 Tagen) zur weiteren Kostenoptimierung von _Cool_ in den _Azure Archive_ Storage verschoben werden. Auf Daten in dieser Ebene kann bei Bedarf nicht sofort zugegriffen werden, und ihre Wiederherstellung verursacht höhere Kosten. Daher sollte berücksichtigt werden, wie oft Daten aus diesen archivierten Backup-Dateien wiederhergestellt werden müssen. Der Abschnitt auf dieser Seite zur Wiederherstellung von Daten aus Archiv-Storage enthält entsprechende Informationen.

Wenn Sie NetApp Backup and Recovery mit dieser Art von Lebenszyklusregel konfigurieren, sollten Sie beim Einrichten des Containers in Ihrem Azure-Konto keine Lebenszyklusregeln konfigurieren.

https://docs.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview["Informationen zu Azure Blob-Zugriffsebenen"^].



[[restore-data-from-archival-storage]]
== Daten aus dem Archivspeicher wiederherstellen

Während die Speicherung älterer Sicherungsdateien in Archiv Storage deutlich kostengünstiger ist als in Cool Storage, dauert der Zugriff auf Daten aus einer Sicherungsdatei in Azure Archive für Wiederherstellungsvorgänge länger und verursacht höhere Kosten.

Wie viel kostet die Wiederherstellung von Daten aus Azure Archive?:: Beim Abrufen von Daten aus dem Azure-Archiv können Sie zwischen zwei Wiederherstellungsprioritäten wählen:
+
--
* *Hoch*: Schnellster Abruf, höhere Kosten
* *Standard*: Langsamerer Abruf, geringere Kosten


Für jede Methode fallen unterschiedliche Abruf- und Anforderungsgebühren pro GB an.  Detaillierte Azure Archive-Preise nach Azure-Region finden Sie auf der https://azure.microsoft.com/en-us/pricing/details/storage/blobs/["Azure-Preisseite"^] .

--



NOTE: Hohe Priorität wird bei der Wiederherstellung von Daten aus Azure in StorageGRID Systemen nicht unterstützt.

Wie lange dauert die Wiederherstellung meiner im Azure-Archiv archivierten Daten?:: Die Wiederherstellungszeit setzt sich aus zwei Teilen zusammen:
+
--
* *Abrufzeit*: Die Zeit, die zum Abrufen der archivierten Sicherungsdatei aus dem Azure-Archiv und zum Platzieren im Cool-Speicher benötigt wird.  Dies wird manchmal als „Rehydratationszeit“ bezeichnet.  Die Abrufzeit ist je nach gewählter Wiederherstellungspriorität unterschiedlich:
+
** *Hoch*: < 1 Stunde
** *Standard*: < 15 Stunden


* *Wiederherstellungszeit*: Die Zeit zum Wiederherstellen der Daten aus der Sicherungsdatei im Cool-Speicher.  Diese Zeit unterscheidet sich nicht von der typischen Wiederherstellungsoperation direkt aus dem Cool-Speicher – wenn keine Archivierungsebene verwendet wird.
+
Weitere Informationen zu den Abrufoptionen für Azure-Archive finden Sie unter https://azure.microsoft.com/en-us/pricing/details/storage/blobs/#faq["diese Azure-FAQ"^] .



--


[NOTE]
====
Das Wiederherstellen eines Volumes oder einer Datei aus dem Archivspeicher kann zusätzliche Zeit in Anspruch nehmen. Der Auftrag bleibt im *Job Monitor* als *In progress* angezeigt, während Backup and Recovery die Wiederherstellung entsprechend der ausgewählten Priorität erneut versucht. Die Wiederherstellung kann im *Job Monitor* überwacht werden; sie ist abgeschlossen, wenn der Auftrag nach allen Wiederholungsversuchen einen endgültigen Status wie *Completed* oder *Failed* erreicht. Eine weitere Wiederherstellung sollte nur gestartet werden, wenn der Auftrag letztlich fehlschlägt.
